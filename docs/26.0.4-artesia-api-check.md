## 发现并修复的问题

1. **QQ 无歌词和获取错误混在一起。** 该固定 MID 的普通歌词接口 `fcg_query_lyric_new.fcg` 返回 `code/retcode = -1901`，无歌词内容；分别使用 MID、数字 ID、两者及 Base64 参数复核，结果一致。兼容的 MusicU `music.musichallSong.PlayLyricInfo / GetPlayLyricInfo` 返回外层 `0`、内层 `24001`、歌词及翻译为空；现有逐字和普通备用读取也无可用结果。没有证据把它修成“获取成功”，也没有增加一个同样空返回的额外请求链。
2. **酷狗空候选被泛化成获取/保存失败。** 两条 195 秒候选的歌词搜索实际返回 HTTP 成功、`status=200`、空 `candidates` / `ugccandidates`。现在用共享的 `LyricUnavailableException` 表达该条录音没有可用歌词；超时、网络、无法解析的响应继续保留不同错误类型。QQ 严格手选入口同样保留这些区别，正常自动读取仍可尝试同 ID 的已有备用读取。
3. **酷狗会返回另一首作品的歌词候选。** 以该专辑的 Piano / last moment 固定哈希查询时，真实服务曾返回柴可夫斯基《The Seasons Op. 37b: June - Barcarole》的候选，时长约 320 秒；旧代码直接取第一条。现在核对已知标题、歌手别名及时间长度，排除明确矛盾后才下载歌词。不抹去 short/full 等版本词；缺失字段不伪装成已核实。旧的仅哈希关联先恢复同一哈希的元数据，避免重启后绕过核对。
4. **Base64 换行及错误类型。** 酷狗下载响应中的折行 Base64 先移除空白再解码，不再因含换行就误作明文；保留既有响应体积上限。缺少必需字段或损坏编码仍报格式异常，空内容报告无歌词。来源能力探针也将无歌词映射为无适用样本，而非网络故障。
5. **自动歌词选择丢失版本信息。** 原先相似度计算去除 short 后，自动读取会直接尝试前 5 条，没有时长门槛，确实可能将 195 秒完整版套给 96 秒短版。`SongSearchResult.durationSeconds` 现在直接保留 QQ `interval`、网易 `duration/dt`、酷狗搜索时长及 LRCLIB 时长，不额外逐首请求详情。自动模式拒绝明显时长冲突、明确 short/full 冲突，以及缺少版本且时长未知的短版候选；人工选择保留。明确版本的本地曲目也不再自动接受无法核实身份的纯文本自定义来源响应，手动来源选择仍可调用。

自动时长容差为本地时长的 4%，最低 5 秒、最高 12 秒，主要排除录音剪辑差异；它不是证明两条录音相同的充分条件。未提供时长记为未知，不伪造 0 秒或宣称精确匹配。同名歌曲的相似度仅用于排序，不再越过版本门槛。

QQ 备用协议只参考并实读了上游 [getLyric.ts](https://github.com/sansenjian/qq-music-api/blob/45d0d275b590d8c3f99270e7f74135873172c71a/src/services/apis/music/getLyric.ts)，固定提交 `45d0d275b590d8c3f99270e7f74135873172c71a`，提交日期 2026-08-27；未复制其实现代码。这里记录实际响应，不将非零业务码泛化为整个 QQ 平台永久失效。
